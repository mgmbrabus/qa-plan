# QA Automation Plan: Запись на профессию «Инженер по тестированию» (Нетология)

> **Критическое ограничение безопасности:**
> Тестирование планируется для production-окружения (`netology.ru`). **Клик по кнопке «Записаться» категорически запрещён во всех сценариях**, чтобы исключить спам лидами в CRM и лишнюю нагрузку на отдел продаж. Тестируются исключительно пути навигации, валидация полей, UI-состояния и маски ввода.

---

# 1. Перечень автоматизируемых сценариев

## 1.1. Навигация и переход к форме записи

* **Сценарий 1.1: Переход через выпадающее меню «Каталог курсов»**
* **Предусловие:** Открыта главная страница `[https://netology.ru/](https://netology.ru/)`.
* **Шаги:**
1. Кликнуть по кнопке «Каталог курсов» в хедере.
2. Выбрать категорию «Программирование».
3. Найти карточку курса «Инженер по тестированию» и кликнуть по ней.


* **Ожидаемый результат:** Происходит переход на страницу профессии `(https://netology.ru/programs/qa](https://netology.ru/programs/qa)`, заголовок H1 и форма присутствуют в DOM.


* **Сценарий 1.2: Переход через витрину направлений на главной странице**
* **Предусловие:** Открыта главная страница `[https://netology.ru/](https://netology.ru/)`.
* **Шаги:**
1. В блоке «Направления обучения» найти карточку направления «Программирование».
2. Кликнуть по ссылке подраздела «Тестировщик ПО» (или «Всего курсов»).
3. Выбрать курс «Инженер по тестированию».


* **Ожидаемый результат:** Корректный редирект на целевой лендинг курса.


* **Сценарий 1.3: Поиск через строку поиска в каталоге**
* **Предусловие:** Открыто модальное окно/каталог курсов.
* **Шаги:**
1. Ввести в поисковую строку инпута `Инженер по тестированию`.
2. Нажать кнопку «Найти курс» (или клавишу `Enter`).
3. Кликнуть по релевантному результату в поисковой выдаче.


* **Ожидаемый результат:** Открывается страница курса.


* **Сценарий 1.4: Якорный переход к форме записи на странице курса**
* **Предусловие:** Пользователь находится на странице курса `[https://netology.ru/programs/qa](https://netology.ru/programs/qa)`.
* **Шаги:**
1. Нажать на кнопку «Записаться» в первом экране (hero-секция).


* **Ожидаемый результат:** Страница плавно скроллится к блоку формы «Запишитесь на курс», блок находится в области видимости (`isDisplayed() == true`).


* **Сценарий 1.5: Сквозной скролл до формы**
* **Предусловие:** Открыта страница курса.
* **Шаги:**
1. Выполнить скролл страницы до блока с формой записи.


* **Ожидаемый результат:** Форма отрисована, инпуты «Имя», «Телефон», «Электронная почта» кликабельны и доступны для ввода.

## 1.2. Позитивные сценарии валидации и ввода (без отправки)

* **Сценарий 2.1: Валидное заполнение базовых данных**
* **Шаги:**
1. В поле «Имя» ввести стандартное имя кириллицей (напр., `Александр`).
2. В поле «Телефон» ввести 10 цифр номера РФ (напр., `9991234567`).
3. В поле «Электронная почта» ввести валидный email (напр., `qa.autotest@example.com`).


* **Ожидаемый результат:** Текст введен во все поля без искажений, в инпуте телефона применилась маска `+7 (999) 123-45-67`, сообщения об ошибках отсутствуют, кнопка «Записаться» перешла в активное состояние (клик НЕ совершается).


* **Сценарий 2.2: Ввод составных и нестандартных валидных имен**
* **Шаги:**
1. В поле «Имя» ввести составное имя через дефис (`Анна-Мария`) или с пробелом (`Иван Петр`).


* **Ожидаемый результат:** Значение принимается, валидация проходит успешно, подстрочные ошибки не появляются.



---

## 1.3. Негативные сценарии и валидация ограничений

* **Сценарий 3.1: Проверка обязательности полей (Blur / потеря фокуса)**
* **Шаги:**
1. Кликнуть в поле «Имя», не вводить текст, перевести фокус на поле «Телефон».
2. Не вводить текст в поле «Телефон», перевести фокус на поле «Электронная почта».
3. Убрать фокус кликом вне формы.


* **Ожидаемый результат:** Под каждым пустым обязательным полем отображается валидационное сообщение («Обязательное поле» / «Заполните поле»).


* **Сценарий 3.2: Невалидные данные в поле «Имя»**
* **Тестовые наборы:**
* Спецсимволы и цифры: `!@#$%^&*()`, `Тестер123`.
* Пробелы (whitespaces): `   `.
* Граничные значения: 1 символ (меньше допустимого) и 150+ символов (проверка лимита буфера/инпута).


* **Ожидаемый результат:** Поле подсвечивается ошибкой («Имя должно содержать только буквы» / «Некорректное имя») либо ввод некорректных символов блокируется маской.


* **Сценарий 3.3: Невалидный формат телефонного номера**
* **Тестовые наборы:**
* Неполный номер: ввод только 5 цифр (`99912`).
* Ввод латиницы и спецсимволов: `abcdef`, `++--()`.


* **Ожидаемый результат:** Буквы и спецсимволы игнорируются маской ввода; при неполном номере выводится ошибка «Номер телефона указан не полностью».


* **Сценарий 3.4: Невалидный формат Email**
* **Тестовые наборы:**
* Отсутствие `@`: `userdomain.ru`.
* Отсутствие доменного имени: `user@`.
* Отсутствие TLD (зоны): `user@domain`.
* Недопустимые символы и пробелы: `user name@domain.ru`, `user@@domain.ru`.


* **Ожидаемый результат:** Выводится сообщение об ошибке формата почты, стили инпута меняются на ошибочные (красная рамка/класс ошибки).

# 1.4. Проверка служебных элементов формы

* **Сценарий 4.1: Ссылки на юридические соглашения**
* **Шаги:** Проверить атрибуты `href` и `target="_blank"` у ссылок «Политика конфиденциальности» и «Пользовательское соглашение».
* **Ожидаемый результат:** Ссылки ведут на актуальные публичные документы и открываются в новой вкладке.


* **Сценарий 4.2: Переключатель кода страны**
* **Шаги:** Кликнуть по дропдауну выбора страны в поле телефона, выбрать другую страну (например, Казахстан или Беларусь).
* **Ожидаемый результат:** Маска ввода и телефонный префикс изменяются на выбранную страну.

# 3. Перечень необходимых разрешений, данных и доступов

1. **Официальное согласование / Safe-list:**
* Уведомление системных администраторов / команды инфраструктуры о проведении автоматизированных UI-проверок с фиксацией IP-адресов CI-раннеров, чтобы избежать срабатывания WAF, Cloudflare или анти-DDoS защиты.


2. **Изолированный тестовый контур (Stage/Pre-prod):**
* Для проведения полноценного E2E-тестирования (включая нажатие кнопки «Записаться» и проверку получения лида в CRM) необходим доступ к staging-стенду с отключенной отправкой реальных заявок клиентам.


3. **Техническая документация:**
* Спецификация валидации полей формы (regex-выражения для email, правила для телефонных номеров разных регионов, список стоп-слов).


4. **Селекторы и верстка:**
* Доступ к исходному коду фронтенда либо согласование добавления стабильных тестовых атрибутов (`data-test-id` / `data-testid`) на ключевые элементы, чтобы исключить завязку на CSS-классы, генерируемые CSS Modules / Styled Components.

# 4. Перечень и описание возможных рисков при автоматизации

* **Риск 1: Случайная отправка формы на Production (Спам в CRM)**
* *Влияние:* Высокое (трата ресурсов сейлз-команды, искажение бизнес-метрик конверсии).
* *Меры снижения:*
* Вынос действия нажатия на кнопку подтверждения в отдельный метод с проверкой флага окружения (`isProductionEnvironment`).
* Использование `assert` на активность кнопки вместо ее клика.
* Обязательное прохождение Code Review перед мерджем тестов.




* **Риск 2: Динамические классы и нестабильные селекторы**
* *Влияние:* Среднее (постоянное падение тестов при деплоях фронтенда).
* *Меры снижения:* Использование Page Object Model, поиск по семантическим тегам, доступным текстовым узлам и атрибутам (`name`, `type`), запрос на внедрение `data-test-id`.


* **Риск 3: Блокировка тестов капчей или защитой от ботов (Cloudflare, reCAPTCHA)**
* *Влияние:* Критическое (тесты не смогут выполняться в CI).
* *Меры снижения:* Отключение капчи на тестовых стендах, добавление тестовых User-Agent в доверенные списки или обход через dev-куки/заголовки.


* **Риск 4: A/B эксперименты на лендинге**
* *Влияние:* Среднее (разные пользователи видят разные вариации формы и структуры страницы).
* *Меры снижения:* Принудительная передача URL-параметров (feature toggles / query-параметры), выключающих A/B тесты во время автотестов.
